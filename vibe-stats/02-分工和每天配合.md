# 分工和每天怎么配合

> 这份文档解决一个问题：**四个人同时动手，怎么不互相破坏。**

---

## 一、最重要的一条规矩

> ## 一个人管一个文件。绝不改别人的文件。

这条规矩不是形式主义，它解决新手小组项目里最致命的三个问题：

**1. 不会互相覆盖。**
两个人同时编辑同一个文件，后保存的那个人会**把前一个人的改动整个覆盖掉**，而且没有任何提示。

**2. 不会产生冲突。**
Git 的"冲突"只发生在**同一个文件**被两个人改的时候。一人一个文件，基本就不会冲突。

**3. 出了问题知道找谁。**
页面颜色不对 → 找 C。数字算错了 → 找 A。不用四个人一起猜。

### 文件归属（第 1 天就定下来，写在群里）

| 文件 | 归谁 | 里面是什么 |
| --- | --- | --- |
| `index.html` | **B** | 页面上有哪些区块、每个区块放什么、文案 |
| `style.css` | **C** | 颜色、字号、间距、手机适配 |
| `data.js` | **A** | 数据本身 + 指标怎么算 |
| `app.js` | **D** | 画图、筛选交互、三种状态 |

### 配套的三条禁令

1. **不许新建文件。** 就这 4 个。AI 让你"新建一个 utils.js"，回它"不行，塞进我自己的文件里"。
2. **不许给文件改名。** 改名会让所有人的页面瞬间白屏。
3. **不许删别人的文件。** 哪怕你觉得它没用。

### 我需要改别人的文件，怎么办？

发群里说，让那个人改，或者让他同意你改。**改完在群里说一句"我动了 app.js 的第 30 行"。**

看起来很麻烦，但比起第 5 天发现三个人互相覆盖、代码全丢，这点麻烦不算什么。

## 二、每天固定三个动作

新手不需要学一堆 Git 命令。**你每天只需要三个动作。**

### 动作一：开始干活前，先"拉"（Pull）

把队友昨天传上去的改动拿到自己电脑上。

**为什么必须做：** 你电脑上的版本是昨天的。不拉下来，你今天就是在旧的上面改，晚上上传时必然打架。

**GitHub Desktop：** 点上方 **Fetch origin** → 如果出现了 **Pull origin**，点它。

**命令行：**

```
git pull
```

### 动作二：每做完一小块，就"提交 + 推送"

**别攒着。** 写一小时再传，中间出了问题你分不清是哪一段坏的。

**GitHub Desktop：**

1. 左边 **Changes**（改动）列表里会列出你改了什么
2. **Summary** 框里写一句说明：`改了首页配色`
3. 点 **Commit to main**
4. 点上方 **Push origin**

**命令行：**

```
git add .
git commit -m "改了首页配色"
git push
```

**说明怎么写：** 写"让人能看懂你干了什么"的话。
- ✅ `加了趋势图`、`修了转化率算成5000%的问题`、`调整了卡片字号`
- ❌ `更新`、`修改`、`提交`、`111`

### 动作三：离开之前，再推一次

哪怕今天只改了一行字，也传上去。**留在自己电脑上的代码，对团队等于不存在。**

然后在群里说一句：`我传了 style.css，改的是卡片颜色`。

---

## 三、完整的一天，长这样

```
09:50  到工位，打开 GitHub Desktop，点 Fetch / Pull
       （拉取队友昨晚的改动）

10:00  15 分钟站会（见下面第五节）

10:15  打开自己的文件开始干活
       每改完一小块 → 保存 → F5 看一眼 → 提交 + 推送

12:00  午饭前推一次，哪怕没做完
       没做完的功能先把入口藏起来，保证页面能打开

14:00  继续。卡住超过 30 分钟就在群里喊

18:00  最后一次推送 + 在群里说一句我改了什么
```

---

## 四、一天里最容易被忽略的三件事

### 1. 推之前，先拉一次

**顺序永远是：先 Pull，再 Push。**

如果你直接点 Push 报错了，八成是因为队友先推了。解决办法：

1. 点 **Pull origin**
2. 如果有冲突，按 [`06-出问题怎么办.md`](06-出问题怎么办.md) 处理
3. 再点 **Push origin**

### 2. 每天结束前，页面必须是能打开的

新的功能做到一半？把按钮先藏起来（CSS 加 `display: none`），或者先不调用它。

**带着白屏过夜，是最伤士气的错误**——第二天别人一拉，看到的是一片空白，会以为是自己弄坏的。

### 3. 页面上看到奇怪的东西，先问，别自己动手改

看到别人区块写错了，不要"顺手帮他改"。**告诉他，让他改。**

他会从中学到东西，而且不会因为两个人同时改而冲突。

## 五、每天 15 分钟站会

**站着开，每人不超过 2 分钟，只回答三个问题：**

| 谁 | ① 昨天传了什么 | ② 今天要传什么 | ③ 卡在哪 |
| --- | --- | --- | --- |
| A | | | |
| B | | | |
| C | | | |
| D | | | |

**三条规则：**

1. **只回答这三个问题，不展开讨论。** 需要细说的，站会后单独拉那个人。
2. **第①问要能对应到一次真实的上传。** 如果连着两天说不出传了什么，说明任务切得太大了。
3. **第③问必须诚实。** "卡在筛选器不会写"说出来的那一刻就已经解决一半了，不说的话会卡到第 6 天。

**站会最后加一个问题，轮着答：**

> "今天做的这个东西，用户看到之后会多知道什么？"

答不上来的功能，当天就砍掉。这是防止第 4 天开始做无用功的最有效办法。

## 六、合并负责人（每周轮一个人）

第一周建议 D 当，之后每周换一个人。他的额外工作是：

- **每天晚上**：从 GitHub 把最新版拉下来，双击 `index.html`，确认页面能正常打开
- **发现问题**：在群里说"今天的页面打不开了，谁改了什么"，并找出是谁，让他修
- **周五**：把这一周的改动看一遍，确认没有重复的、互相矛盾的

**合并负责人不是领导，也不写别人的功能。** 他只负责一件事：**保证主线一直是好的。**

### 每天的 2 分钟检查

拉下来之后：

1. 双击 `index.html`
2. 看三处：有没有数字、有没有图、按 F12 有没有红字
3. 有问题就在群里说，**当天修掉，不许过夜**

## 七、什么时候该用"分支"

**新手第一周：不用分支。** 直接在 `main` 上改，因为我们一人一个文件，几乎不会撞。分支会增加一个你要记的概念，收益不大。

**出现下面这些情况，才值得学分支：**

- 有人想做一次"大改版"，可能会把页面改坏
- 项目已经上线了，但你们要同时开发下一版
- 某个人要试一个不确定能不能成的想法

到那时候照着做就行（GitHub Desktop 里有 **New branch** 按钮），或者让 D 来操作。**现在不用管。**

---

## 八、如果把项目做完了还有点时间

按优先级排：

1. **补口径说明**——每个指标怎么算的，写到页面上。这件事的价值比其他所有事加起来都高。
2. **补三种状态**——空数据、加载中、出错。
3. **手机适配**——窗口拉到最窄看一遍。
4. **加一个功能**——只有前三条都做完才考虑。

**不要在第 6 天加新功能。** 加功能一定会引入新问题，而你没有时间修了。

---

## 九、一句话总结

如果你只记三件事：

1. **开工先拉，做完就传。**
2. **只改自己那个文件。**
3. **下班前页面必须是能打开的。**
